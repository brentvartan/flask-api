### [BLOCKER] `signal_pipeline.py:636-664 (with app/services/scheduler.py:346)`

> **[FIXED]** ac24dd2
**Problem.** A triaged-out signal never gets an "enrichment" key written into its description, but the backlog drain selects rows by exactly that absence. So every signal the Haiku gate rejects is re-selected — and re-triaged — on every subsequent run, forever. Because the backlog is ordered created_at ASC and rejected rows never leave the set, they permanently occupy the drain slots and the genuinely un-scored corpus stops draining. This re-creates the under-sampling the whole P2 batch exists to fix, and it burns money doing it.

**Evidence.** signal_pipeline.py:661-663 — `if enrichment.get("enriched"): meta["enrichment"] = enrichment` — the only writer of that key; on the triage-out path (line 641-643) `enrichment` stays `{}` so the key is never written. scheduler.py:345-346 — `.filter(Item.item_type == "signal").filter(~Item.description.contains('"enrichment"')).order_by(Item.created_at.asc())`. Failure scenario: night 1 saves 8,500 signals, scores 2,000, ~60% triaged out = ~1,200 rejected rows with no "enrichment" key. Night 2 budget 2000 = ~1,050 new + ~950 backlog, and the backlog query returns those same rejected rows (oldest, still matching the filter). By night 3 the accumulated rejected set (~1,800+) exceeds the ~950 backlog slots, so every backlog slot is spent re-triaging a row already rejected and the 6,500-row deep-sweep backlog is never scored. Cost of the waste: 950 x $0.0018 = $1.71/night = ~$624/yr in pure re-triage.

**Fix.** On the triage-out branch, write a sentinel that the backlog filter excludes — e.g. set meta["enrichment"] = {"enriched": False, "skipped_by": "triage", "at": ...} before _save() at line 643, or change _backlog_item_ids to also exclude rows containing '"triage"' with worth_scoring false. The same filter at app/api/enrich/routes.py:100 (unenriched_only) has the identical defect and needs the same treatment.

### [BLOCKER] `routes.py:100-155`

> **[FIXED]** ac24dd2 — _fair_share round-robins across collectors
**Problem.** The P1 change that made this endpoint return 202 and run in a background thread removed the only thing that was bounding it. Previously the inline call blew through gunicorn's 300s timeout and the worker died, killing the scan; now every press runs a full scan to completion. Three multipliers stack: (1) `@limiter.limit("5 per minute")` uses flask-limiter's default override_defaults=True, which REPLACES the global 200/day + 60/hour caps with 5/min = 7,200/day; (2) the endpoint takes no job lock, so N presses = N concurrent run_scan_now calls; (3) fingerprint dedup means repeat runs save ~0 new signals, so to_process fills entirely from _backlog_item_ids — the same oldest 2,000 un-scored rows — and every concurrent run pays full Anthropic price for the identical rows. Any authenticated teammate (list_scans auto-seeds a scan for every user on first visit) can do this.

**Evidence.** routes.py:102 `@limiter.limit("5 per minute")` (verified flask_limiter 3.9.0: `Limiter.limit` signature has `override_defaults` defaulting to True, so extensions.py:38 `default_limits=["200 per day", "60 per hour"]` does not apply here); routes.py:148 `threading.Thread(target=_run_bg, daemon=True).start()`; routes.py:117-119 docstring confirms run_scan_now is called directly and "never consults the cooldown"; scheduler.py:673-676 `to_process = list(new_item_ids[:enrich_budget])` then `to_process += _backlog_item_ids(...)`. Priced from this code at SCAN_ENRICH_BUDGET=2000: 2,000 Haiku triage calls at ~1,050 in / 150 out = $3.61, plus ~800 Sonnet survivors at (8,400 cached-read + 400 uncached in, ~900 out) = $13.78 => ~$17.50 per press. A frontend retry loop stuck at the 5/min ceiling for one hour = 300 runs = ~$5,250; the limit as written permits 7,200 runs/day = ~$126,000/day.

**Fix.** Pass override_defaults=False on the limiter so the 200/day global cap still applies, drop the per-minute allowance to something like 2/hour, and gate the background thread behind _acquire_job_lock(app, f"manual_scan_{scan_id}", ttl_seconds=...) so a second press is a no-op rather than a duplicate paid run. Also make _backlog_item_ids claim rows (or exclude in-flight ids) so two runs cannot score the same signal twice.
